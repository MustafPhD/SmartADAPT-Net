# Data Dictionary

This document describes the expected data structure for running the SmartADAPT-Net code repository.

Raw participant data are not included in this repository. Users should provide their own local Phase 1 and Phase 2 data folders using the structures described below.

---

## Phase 1 data structure

Phase 1 data should be organised as one folder per activity of daily living (ADL). Each ADL folder should contain one CSV file per participant.

Example:

```text
Phase 1 Data/
├── Brushing Teeth/
│   ├── P101.csv
│   ├── P102.csv
│   └── ...
├── Mopping_Hoovering/
│   ├── P101.csv
│   ├── P102.csv
│   └── ...
├── Shelving Items/
├── Walking/
├── Washing Dishes/
└── Washing Face/
```

Each participant CSV may contain the full CoreMotion recording columns, but the model uses six inertial channels: tri-axial user acceleration and tri-axial rotation rate.

### Required Phase 1 columns

| Column name | Description | Used by model |
|---|---|---|
| `motionUserAccelerationX(G)` | User acceleration, x-axis, in g | Yes |
| `motionUserAccelerationY(G)` | User acceleration, y-axis, in g | Yes |
| `motionUserAccelerationZ(G)` | User acceleration, z-axis, in g | Yes |
| `motionRotationRateX(rad/s)` | Rotation rate, x-axis, in rad/s | Yes |
| `motionRotationRateY(rad/s)` | Rotation rate, y-axis, in rad/s | Yes |
| `motionRotationRateZ(rad/s)` | Rotation rate, z-axis, in rad/s | Yes |
| `motionGravityX(G)` | Gravity component, x-axis, in g | No |
| `motionGravityY(G)` | Gravity component, y-axis, in g | No |
| `motionGravityZ(G)` | Gravity component, z-axis, in g | No |
| `motionYaw(rad)` | Device yaw angle, in radians | No |
| `motionRoll(rad)` | Device roll angle, in radians | No |
| `motionPitch(rad)` | Device pitch angle, in radians | No |

The model input channel order is:

```text
motionUserAccelerationX(G)
motionUserAccelerationY(G)
motionUserAccelerationZ(G)
motionRotationRateX(rad/s)
motionRotationRateY(rad/s)
motionRotationRateZ(rad/s)
```

This order must remain fixed across Phase 1 training, Phase 2 replay, and watchOS deployment.

## Phase 2 data structure

Phase 2 data should be organised as one folder per participant. Each participant folder should contain session CSV files and one `manifest.csv` file.

Example:

```text
Phase 2 Data_F/
├── P201/
│   ├── manifest.csv
│   ├── P201_D01_S001.csv
│   ├── P201_D01_S002.csv
│   └── ...
├── P202/
│   ├── manifest.csv
│   └── ...
└── P217/
```

Session filenames follow the structure:

```text
P201_D01_S001.csv
```

where:

| Element | Meaning |
|---|---|
| `P201` | Participant identifier |
| `D01` | Deployment day |
| `S001` | Session number for that participant/day |

---

## Phase 2 session CSV columns

Each Phase 2 session CSV should contain the following columns:

| Column name | Description |
|---|---|
| `Timestamp` | Timestamp for each recorded motion sample |
| `motionRotationRateX(rad/s)` | Rotation rate, x-axis |
| `motionRotationRateY(rad/s)` | Rotation rate, y-axis |
| `motionRotationRateZ(rad/s)` | Rotation rate, z-axis |
| `motionUserAccelerationX(G)` | User acceleration, x-axis |
| `motionUserAccelerationY(G)` | User acceleration, y-axis |
| `motionUserAccelerationZ(G)` | User acceleration, z-axis |
| `motionGravityX(G)` | Gravity component, x-axis |
| `motionGravityY(G)` | Gravity component, y-axis |
| `motionGravityZ(G)` | Gravity component, z-axis |
| `motionYaw(rad)` | Device yaw angle |
| `motionRoll(rad)` | Device roll angle |
| `motionPitch(rad)` | Device pitch angle |
| `PredictedClass` | Prediction generated by the deployed watch model |
| `UserConfirmation` | User feedback after prediction |

The `UserConfirmation` column has two possible meanings:

| Value | Meaning |
|---|---|
| `Yes` | The predicted class was correct |
| ADL name | The predicted class was wrong, and this value is the corrected ADL |

## Phase 2 manifest columns

Each participant folder should contain a `manifest.csv` file with one row per session.

| Column name | Description |
|---|---|
| `participant` | Participant identifier |
| `day` | Deployment day |
| `session` | Session number |
| `UserConfirmation_true` | Final confirmed or corrected ADL label |
| `PredictedClass` | Original watch prediction |
| `n_rows` | Number of rows in the session CSV |
| `file` | Path to the session CSV |
| `improving` | Optional diagnostic flag |
| `inconsistent` | Optional diagnostic flag |

The replay script uses `UserConfirmation_true` as the deployment reference label.

## Canonical Phase 2 replay output

Code 2 produces canonical replay CSV files used by Code 3. The main output is:

```text
phase2_replay_window_level_CODE1_canonical_compatible.csv
```

Important columns include:

| Column name | Description |
|---|---|
| `participant` | Participant identifier |
| `day` | Deployment day |
| `session` | Session number |
| `confirmed_class` | Participant-confirmed or corrected reference label |
| `watch_pred` | Original saved watch prediction |
| `base_pred` | Prediction from the frozen Base model |
| `global_pred` | Prediction after complexity-aware modulation |
| `proto_pred` | Prediction from prototype branch |
| `final_pred` | Final fused prediction |
| `base_correct` | Whether Base prediction matched confirmed class |
| `global_correct` | Whether Global/CAM prediction matched confirmed class |
| `proto_correct` | Whether Prototype/CDP prediction matched confirmed class |
| `final_correct` | Whether Final prediction matched confirmed class |
| `p_base_true` | Base probability assigned to confirmed class |
| `p_global_true` | Global/CAM probability assigned to confirmed class |
| `p_proto_true` | Prototype/CDP probability assigned to confirmed class |
| `p_final_true` | Final fused probability assigned to confirmed class |
| `complexity_session` | Mean calibrated complexity across the three analysis windows |
| `proto_active` | Whether at least one participant-specific prototype was active |
| `deployment_block` | Five-day deployment block used for temporal analysis |

---

## Privacy note

Raw participant data should not be committed to GitHub. The repository is intended to share code, documentation, configuration templates, and optional synthetic/example data only.
